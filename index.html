The core mechanic

The clothespin kill.

Forget cards and apps. In Among Us: Parasite, imposters carry a physical weapon, and it is a neon clothespin. 300 players, 4 shifts, 2 days and one very suspicious pocket.

How a kill works

  1. Each Imposter is secretly given a pocket full of neon clothespins. These are the Parasites.
  2. To eliminate a Crewmate, clip a Parasite onto their shirt, jacket or backpack without them noticing.
  3. If the Crewmate feels the clip and turns around, the Imposter must pretend nothing happened. Pure physical comedy.
Safety rule: clips go on clothing or bags only, never skin or hair. No grabbing, no chasing.
Small tasks

Between the chaos, do your tasks.

Every Crewmate gets a Task Card. Task stations are set up around the hall, staffed by volunteers. Finish a 30-second task, get a stamp. Imposters get a fake card and have to look busy doing decoy tasks. Each station fits 3 players at a time.

Mission log · AI workflow

How this ship was actually built.

This is an honest, detailed account of the build: what AI did, what I did, where it failed, and why the decisions were made. Written for the evaluators so the interview can go somewhere useful.

The Model & the Tools

The entire site was built in different conversations with Claude Sonnet 5.5 and Gemini 3.1 Pro through both apis and platforms. No Copilot, no v0, small fixes were made using vs code by me. The AI wrote the HTML, CSS and JS. I directed every decision.

Why Claude over Antigravity for this? Because of my previous works with claude I had a familiarity with the platform.

Why not a framework like React or Next? The brief said laptop-first, self-contained, deploy on Vercel. A single HTML file can do all of that with zero build step. Adding a framework would have meant a build pipeline, a package.json and a node_modules folder just to serve static content.

Prompt #1: The Brief as Context Dump

The first message was definitely not "make an Among Us website". It was a full context dump: the task PDF, four screenshots of the old Spark registration site for inspiration, the game mechanics I had designed on my own and further refined by gemini (the clothespin mechanic, the chaos tasks, the tribunal), a reference screenshot of the comic-style hero I wanted, and explicit constraints.

The principle here is that AI works on pattern completion. If you give it thin context, it fills the gaps with whatever is statistically most common, which is usually a generic Bootstrap site. A rich context forces it into your specific corner of the design space.

What I gave it: the PDF, 4 reference screenshots, the registration form structure from the old site, the game mechanics, a style reference image, "laptop-first", "Among Us theme", "no prior experience needed". That is what the first message looked like.

Iteration 1 → 2 → 3: Direction, Not Requests

The first version was goofy. The second was too plain. The third matched the vision. Each time I gave specific directional feedback, not vague requests.

  • Version 1: "too goofy, make it professional and stylish." But I also added new requirements: light/dark mode, emergency button for register, all the game mechanics explained, tasks section, and the new form fields (program, year).
  • Version 2: "design is perfect, continue with the game mechanics now". I gave it the clothespin mechanic details, the chaos tasks rationale, the poster reference URL, the footer image, and asked it to keep the specific design language from the reference.
  • Version 3 (current): detail refinements. Logo, cursor, title glitch, light mode text smudge were fixed.
The lesson about chaos tasks: Thought that the 2 mins gap between chaos tasks would have been just the students talking amongst themselves, So instead added additional tasks that are to be performed to collect stamps for Shield.

The Backend Decision

Three different approaches were tried before the form worked:

  • The First Approachusing google forms embed : Firstly I thought of adding a google form embed for registration then considered it pretty basic and moved to the next approach.
  • Attempt 1 — fetch() with no-cors: the request fired but the browser discarded the response. The page couldn't tell if it worked, so it showed success even on failure.
  • Attempt 2 — fetch() with JSON headers: Google's Apps Script deployment was correctly set to "Anyone", but the browser blocked it for having no CORS header on the reply. The button did nothing.
  • Attempt 3 — JSONP: inject a <script> tag whose src is the request URL. Browsers never block script loads. The server wraps its response in the callback function name and the browser executes it. This bypasses CORS entirely without needing server-side changes.

The root problem was a naming clash I found with a simulation test: the poster artwork and the program dropdown both had the internal name pg. When you pressed Register, the form code picked up the SVG gradient instead of the dropdown value and crashed silently. The JSONP change and the crash were separate bugs fixed in the same pass.

How the simulation caught it: Claude ran the page in a headless browser (jsdom) inside the conversation itself, filled the form and pressed submit programmatically, and read back whether the success screen appeared. That is how the duplicate-ID crash was found. No DevTools, no live browser.

Three Real Bugs That Would Have Shipped

Without testing, these would have gone live:

Bug 1

The title flickered when the cursor crossed its edge. The heading had a hover animation that conflicted with its entrance animation. The title's skew meant the mouse kept entering and leaving. Fixed: title ignores mouse entirely.

Bug 2

The Register button did nothing. Two elements in the same page shared the name pg (the poster gradient and the program dropdown). The form code grabbed the SVG element at submit, got undefined instead of a string, and crashed. Fixed: renamed the SVG elements.

Bug 3

Light mode had smudged headings. In dark mode, cream text on a dark background with a black outline and black offset shadow looks like a comic. In light mode, black text with a black outline and a black shadow on a cream background turns into a single smeared blob. Fixed: headings use white text with the outline in light mode, so the contrast is correct in both modes.

What AI Is Bad At (On This Project)

This is the part most people leave out of their AI workflow write-ups.

Bad at this

Catching its own naming collisions. The pg clash only appeared when I ran a simulation. The AI generated a perfectly readable gradient and a perfectly readable dropdown in separate parts of the file and never considered that they shared a namespace. Large files are where this happens, and a single-file site is basically one giant namespace.

Bad at this

Cross-origin constraints. The AI's first two backend approaches were plausible but wrong for this specific deployment. It knew about CORS in general. It did not know that Google Apps Script adds no CORS header to responses by default, which is not standard behaviour. That required me to recognise the pattern from the error and push for JSONP specifically.

Bad at this

Knowing when it is in demo mode. The page ran in the Claude artifact preview, which is a different runtime from a deployed Vercel site. Several early tests looked fine in preview and failed in deployment because preview has different network permissions. The simulation work was to close that gap.

The honest summary: AI is a very fast, very capable junior developer. It does not have the experience to know which corner cases will bite you at 1 AM before a deadline. That part is still on you.
